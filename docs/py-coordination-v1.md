# Py Coordination v1 — межпроектные обращения

**Владелец контракта:** `agent-ssh-gateway`. **Источник истины:** Gitea Issues и Gitea Issue Comments.
Нет нового независимого хранилища задач. Один Issue в репозитории получателя — один разговор
между GPT и его последующими чатами. PR не является coordination Issue.

## Рабочий цикл

1. Перед началом работы, после переезда в новый чат и перед handoff вызвать
   `coord_inbox(project="<зарегистрированный проект>")` или
   `coord_board(project="<зарегистрированный проект>")` для представления Kanban.
   При необходимости открыть
   `coord_open(project, issue_number)` для истории и последнего состояния.
2. Если ошибка относится к другому проекту, вызвать
   `coord_create(source_project, target_project, title, message, request_key)`.
   **Целевой проект — владелец** решения; чужой код и production не менять.
3. GPT проекта-получателя отвечает `coord_accept(...)`; дальнейшие обсуждения
   `coord_reply(...)`. Состояние и доказательства — `coord_update(...)`.
4. Возможные переходы: `open → accepted → waiting_review → resolved`; из
   `waiting_review` можно вернуться к `accepted`. Ответ `coord_reply` не
   меняет состояние. После `resolved` комментарии через API запрещены.
5. Для межпроектной блокировки `waiting_review` означает: исполнитель приложил
   PR, exact SHA, CI и запрашивает проверку другой стороны. Только после успешной
   проверки исходный проект публикует `resolved` с фактическим доказательством.
   **Gitea issue остаётся открытым до отдельно подтверждённого закрытия
   владельцем** — v1 не выполняет PATCH issue state автоматически.

## Ключи повторов и безопасность

Каждая операция записи требует **уникальный заранее назначенный `request_key`**
(8–100 символов, lowercase letters/digits/._-). При повторе той же операции
использовать **тот же ключ**, а не создавать новый. При конфликте ключа с иным
текстом, неизвестном исходе POST или слишком большой истории — отказ.
Повторно выполнить POST на новый ключ после сетевого сбоя нельзя: сначала
перечитать `coord_inbox` / `coord_open`. Чтение `coord_board`/`coord_inbox` ограничено первыми 500 Gitea Issues;
если выборка может быть неполной, явно возвращается `truncated=true`.
`coord_open` и браузерный `/api/coordination/thread` читают не более 100
комментариев (две страницы). Если история длиннее либо Gitea повторяет
страницы, возвращаются только уникальные наблюдавшиеся комментарии и
`history_truncated=true`; итоговый `coord_state=null` означает **неизвестно**.
Отсутствуют `close_state_sha256` и `close_content_sha256`: неполное чтение
никогда не разрешает запись, закрытие Issue или вывод об отсутствии event.
Для короткой полной истории эти поля и проверяемое состояние сохраняются.
Браузерная доска исключает непроверенные треды, передаёт их номера в
`incomplete_thread_numbers` и отмечает всю выборку `truncated=true`.
Для записи выполняется строгая проверка истории до 5000 Issues или комментариев:
при превышении лимита новая запись не разрешается, чтобы исключить
непроверенные дубликаты. Reconciliation не гарантирует exactly-once при конкурентных созданиях:
для этого в последующей версии нужен durable coordination outbox с атомарными
резервациями.

Текущий scope: только **зарегистрированные source_project/target_project**.
Обычно repository slug совпадает с project ID. Если имя чувствительно к регистру
или отличается, исходный `projects.yaml` обязан содержать явный
`gitea_repo: gpakoh/NOD_gateway` (для `nod-gateway`). MCP и браузер
используют точный slug из доверенного registry metadata, но сохраняют project ID
в source_project-маркере. Неверный owner, невалидный slug и испорченная
явная привязка отклоняются *до* обращения к Gitea — никакого lowercase
fallback или автоматического создания второго репозитория. Deployment с
отдельно смонтированным `projects.yaml` требует синхронизации этого
поля на сервере и повторной проверки живого сервиса.
Gitea владелец `MCP_COORD_GITEA_OWNER` (по умолчанию `gpakoh`),
разрешение Gitea на запись в целевой репозиторий. Проект-источник указывается
автором обращения, то есть это **заявленная** принадлежность, а не право записи
в его репозиторий. Идентичность автора записи берётся из удостоверенного
Gateway-сеанса и записывается как непрозрачный 16-hex псевдоним, без публикации
токенов. Общая Gitea service-account identity не эквивалентна личности GPT;
входящие сообщения из Gitea считаются **недоверенным содержимым**, а не
инструкциями к исполнению.

`coord_inbox`, `coord_board` и `coord_open` доступны в `mcp_client`, в том числе safe
mode, с `mcp:repo`. Операции создания, ответа и изменения состояния доступны
только в `mcp_client_write` и требуют `mcp:repo` и удостоверенного вызывающего
сеанса; Gitea token должен иметь `push` в целевом репозитории. Ошибки
контракта проходят fail-closed; неподтверждённая запись возвращает
`MUTATION_OUTCOME_UNKNOWN` и не повторяет POST слепо.

## Первый межпроектный кейс

`source_project=business-analytics-service` →
`target_project=agent-ssh-gateway`, «candidate_cleanup удерживает завершённый
кандидат»; к обращению прикладываются:
`candidate-business-analytics-service-feat-a3-postgres-scope-access-20261019-f8e27a4fe165-2d57a5504b3e`,
PR #1, merge commit `d32b3c0444cbbebcbab8cd028d38f0563a54a18a`,
CI #18877 SUCCESS, запрос `61aa4e7a-4bf2-4830-82ea-c34169777831`.
Контракт `_candidate_has_active_evidence()` сейчас считает `.ai-bridge/current-plan.md`
блокирующим по факту существования; реальная причина у кандидата должна
быть подтверждена на runtime. После исправления requester повторяет штатную
очистку и отвечает в том же треде.

## Браузерная доска (read-only)

Веб-Gateway предоставляет адрес `/coordination?project=agent-ssh-gateway` и
авторизованные GET `/api/coordination/board` и
`/api/coordination/thread`. Он показывает те же четыре состояния из Gitea,
умеет открыть историю и перейти к исходному Issue. Доска предназначена только
для master API identity или веб-пользователя с ролью `admin`; агентские ключи
и обычные веб-роли не получают доступ.

Браузер использует существующую HTTP-only сессию веб-Gateway. Он **не получает**
Gitea token, MCP OAuth credential или сведения о секретах. Получение данных
делает серверный GET-only адаптер, применяющий ту же функцию проекции
`app/coordination_logic.py`, что и MCP. Данные и статусы не
копируются в другую БД.

Для включения оператор отдельно предоставляет *ограниченный только чтением*
credential `COORDINATION_GITEA_READ_TOKEN` через конфигурацию контейнера.
Нужен отдельный read-only PAT **того же Gitea-аккаунта**, от имени которого
MCP публикует Coordination events: иначе проверка авторства событий перестанет
быть корректной. `COORDINATION_GITEA_WRITER_LOGIN` по умолчанию `gpakoh`;
если предъявленный read-only PAT принадлежит другому аккаунту, чтение
завершается ошибкой без ложного отображения статуса.
Опциональны `COORDINATION_GITEA_OWNER` (по умолчанию `gpakoh`) и
`COORDINATION_GITEA_API_BASE` (по умолчанию
`https://gitea.example/api/v1`; только HTTPS). Значение credential нельзя
указывать в issue, логе, команде или браузере. В случае отсутствия credential
GET endpoint возвращает 503; **автоматического fallback на привилегированный
GITEA_TOKEN нет**. Изменение конфигурации и production credential —
отдельный контролируемый операторский шаг.

GET-запросы ограничены зарегистрированными исходными проектами (не candidate),
25 карточками за раз и физическим read-only окном из первых 500 Issues.
`truncated=true` показывает неполную выборку. Браузер никогда не трактует
Gitea комментарии как инструкции, не вставляет HTML от Gitea и не выполняет
POST/PATCH/DELETE. Создание и изменение состояний по-прежнему проходят
через разрешённые MCP-инструменты с проверкой права записи. Не перепутать
браузерный read-only UI с нативной Gitea Projects Kanban-доской.

### Post-deploy проверка браузерного маршрута

Стандартный `deploy-from-registry.sh` запускает
`scripts/coordination_browser_smoke.py` **внутри работающего**
`web-ssh-gateway` после проверки готовности сервисов. Smoke выполняет только
локальные GET, проверяет запрет анонимного доступа к HTML/API, аутентифицированный
ответ страницы, `Cache-Control: no-store` и JSON-форму доски.

При ненастроенном `COORDINATION_GITEA_READ_TOKEN` ожидается **точное 503**
с сообщением об отсутствующем read credential. Когда credential настроен,
проверка требует успешный read-only ответ и четыре колонки. Неверная
аутентификация, неожиданная публикация страницы без авторизации, ошибка
upstream либо неверная форма данных блокируют обычный release, а не объявляются
успешной приёмкой. Smoke не выполняет POST/PATCH/DELETE и не выводит ни API key,
ни PAT, ни тела ошибок Gitea. Это release-contract smoke, **не** замена
операторской проверки браузера после настройки credential.

## Ограничения MVP

Read-only веб-интерфейс доступен при настроенном отдельном credential, но это **не**
нативная Gitea Projects Kanban и не постоянно работающий agent scheduler. GPT увидит входящие обращения при
следующем вызове `coord_inbox`, но уведомление **само по себе** не создаёт
новый ход ChatGPT и не гарантирует мгновенную доставку. Вебхуки, durable
read cursors, cross-project агрегатор, подписки, атомарная дедупликация и
возможность заверенного согласования closure — отдельный следующий этап.

## Роль в Gateway

При работе серверным worker выполнять только разрешённое задание в изолированной рабочей области. Передать diff, проверки и отчёт управляющему агенту; не выполнять commit/push/merge/release, не создавать ветки и не закрывать Issue. Упоминания доставки и gateway-finish-task ниже относятся к управляющей роли. Использовать только реально доступные инструменты; skills не расширяют полномочия.

# Качество кода для Gateway

## Выбрать проверяемый результат

- Прочитать задачу, применимые AGENTS.md, контракт компонента и текущую реализацию. При работе через Gateway открыть актуальные схемы инструментов и точную ревизию. Соблюдать границы уже данного поручения.
- Сформулировать конкретное наблюдаемое изменение и существенные условия совместимости. Для ревью отделять найденный дефект от предложения улучшить стиль.
- Выделить один завершённый участок работы. Сохранять существующий ясный локальный код; не расширять исправление до архитектурной перестройки без подтверждённой необходимости.
- Если последовательные правки не меняют один и тот же отказ, остановить наращивание патчей и проверить исходную гипотезу по журналам, владельцам состояния и реальному пути исполнения.

## Установить причину

- Показать воспроизводимый вход, ошибочный результат и ожидаемое поведение. По возможности сначала получить регрессию, падающую из-за нужного дефекта, затем исправить код.
- Сохранять прямые диагностические доказательства, если полноценный тест в доступной среде невозможен. Честно указать ограничение; не заменять проверку assert на константу, фиктивный mock или тест, читающий собственную реализацию.
- Различать ошибку приложения, ошибку зависимости, неверную конфигурацию и недоступное окружение тестов. Не маскировать их единым успешным fallback.
- Сопоставлять гипотезу с реальными HTTP-статусами, типами исключений и контрактами ответов. Не классифицировать транспортную ошибку по случайной строке внутри пользовательского сообщения.

## Исправить контракт и состояние

- Проверять внешний ввод на границе: типы, размеры, обязательные поля, полномочия и идентичность ресурса. Сохранять важные различия: false, отсутствие, строка, ноль и неизвестный результат.
- Отдельно проверять bool, если контракт требует целый числовой идентификатор; учитывать особенности языка. Обновлять публичную схему и её интеграцию вместе с runtime-проверкой.
- Использовать понятные структуры и статусы, сохраняющие существенные инварианты. Не подавлять ошибки типизации широким Any, ignore или отключением проверок вместо исправления модели данных.
- Передавать проверенные данные дальше без бесполезного дублирования валидации. Повторять проверки там, где ресурс мог измениться: права, lease, HEAD, владение и конкурентное состояние.
- Явно определять владельца изменяемого состояния. Изолировать независимые задачи. При действительно общем ресурсе обеспечивать атомарный захват, межпроцессную защиту и долговечность в соответствии с контрактом; одного in-memory lock недостаточно для нескольких процессов.
- Сохранять совместимость старых данных и старых клиентов в пределах требований. Миграцию и восстановление оценивать отдельно от поведения на новой пустой базе.

## Обработать внешние эффекты и сбои

- Для операции с внешним эффектом определить durable identity, намерение до отправки, способ подтверждения и восстановление после сбоя.
- После тайм-аута записи проверять состояние прежней операции через предусмотренный receipt/status. Не повторять POST, merge, close или deploy вслепую; не менять operation key ради повтора.
- Различать accepted, verified identity, successful conclusion и подтверждённое состояние сервиса. Не превращать неизвестность в success или уверенный failure без доказательства.
- Если система не даёт атомарной гарантии, явно описать оставшееся окно гонки и существующую защиту. Не обещать exactly-once на основании одного локального журнала.
- Сохранять проверку прав и запреты сервером. Инструкции skill не подменяют авторизацию, блокировки или аудит. Не обходить отказ инструментов альтернативным каналом.

## Подобрать достаточные проверки

- Проверять наблюдаемое поведение через подходящую публичную границу. Контролируемый mock полезен для контракта, но не доказывает живую БД, качество реальной модели или передачу оригинального файла.
- Выбирать регрессии по изменению: неверный/пограничный ввод, прежний успешный случай, сбой зависимости, конкурентность, restart или потеря ответа — только когда эти свойства затронуты.
- Для межпроцессной блокировки проверять несколько процессов; для persistence — восстановление; для HTTP/MCP — реальную используемую схему и сериализацию. Соотносить глубину тестов с риском и критериями задачи.
- Выполнить обязательные lint/typecheck/test/CI проекта. Для обратимой низкорисковой правки текста использовать подходящую простую проверку; не создавать искусственную тестовую инфраструктуру.
- Применять анализ сложности, дублирования и мутационные проверки целенаправленно к подходящему коду. Сначала установить поддержку языка, воспроизводимость и стоимость. Не объявлять Crapper/Dryer/Mutator установленными или пройденными без фактического запуска.
- Следовать обязательным метрикам repository. При отсутствии принятого порога использовать метрику как диагностический сигнал: не дробить функцию и не объединять разные доменные правила исключительно ради числа. Подробности и вопросы ревью читать в [references/review.md](references/review.md).

## Передать проверенный результат

- Перед публикацией проверить scope, неожиданные изменения, актуальность base и точный HEAD проверок. Использовать защищённый путь PR/CI; не отправлять результат напрямую в default branch.
- Для разрешённых merge, release, отчёта, закрытия Issue и очистки применять доступный gateway-finish-task. При его недоступности читать правила проекта и соблюдать исходное поручение; не устанавливать новый обязательный блокер из отсутствия вспомогательного skill.
- В отчёте связать дефект, причину, изменение и доказательства. Указать ограничения и оставшиеся критерии. Вести краткие durable checkpoints для восстановления; не засорять основной диалог полным журналом каждой команды.
